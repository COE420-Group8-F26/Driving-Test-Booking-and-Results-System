The Incremental Model was selected for the Driving Test Booking and Results System: the system will be divided into smaller increments, with each increment adding functionality to the previous version.

The Incremental Model works well for this project because it can be divided into separate functional parts. For example, the first increment can cover user registration and login, whilst another increment could cover test booking and scheduling. Following that theme, later increments can continue to introduce examiner assignments, test results, notifications, test history, etc.

This approach allows each part of the system to be developed and reviewed before adding further functionality. It also provides flexibility in case any requirements need to be refined during the development of the project, since changes can be handled in later increments.

As for major drawbacks or overheads, Table 1 lists a few possible obstacles and a tentative plan to tackle them.

Major Drawback / Overhead:

Careful planning of increments is required to avoid the possibility of creating dependencies between them and making later development difficult.
Integration between increments can cause issues. Some of the new functionality could conflict with previous increments.
Changes to any of the earlier requirements could affect the later increments, especially if it’s a change to a core feature (like booking, for example).
Repeated testing (for system review) could create overhead, since each increment would require its own evaluation.

Plan to Manage or Reduce It:

The main system requirements will be identified early, and related features will be grouped into logical increments before development begins.
Each new increment will be integrated and tested with the existing system before the team moves on to the next increment.
Core requirements and dependencies will be reviewed before each increment, and project documentation will be kept updated when changes occur.
Testing will be performed as each increment is completed to detect problems early and reduce the amount of rework required later.
